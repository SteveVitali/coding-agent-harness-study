## A. Orientation

**Classification correction.** The provisional label "VS Code-first coding product" is stale at this commit. The repo is a Bun monorepo (`package.json:1-12` workspaces) whose center of gravity is a publishable SDK: `sdk/packages/{shared,llms,agents,core,sdk,ui}` all at v0.0.69, with `apps/{vscode,cli,cline-hub,vscode-rollout,examples}` as hosts. The classic extension engine (`recursivelyMakeClineRequests`, `parseAssistantMessage`) no longer exists anywhere in `apps/vscode/src` (repo-wide grep: zero hits); the extension is now a host adapter over `@cline/core` via a ~90-file bridge layer in `apps/vscode/src/sdk/`.

- **Languages/stack:** TypeScript throughout; Bun 1.3.13 toolchain, Node >=22 runtime (`AGENTS.md:1`). Webview: React + Radix/HeroUI + Tailwind (webview-ui/package.json deps). CLI TUI: OpenTUI React (`package.json:overrides @opentui/*`). Desktop example: Tauri v2 (Rust) + Next.js (`AGENTS.md` desktop-app section).
- **Layering** (sdk/ARCHITECTURE.md:26-41, doc, corroborated by package deps): `shared` → `llms` (providers) → `agents` (stateless loop) → `core` (stateful orchestration, sessions, hub) → host apps.
- **Entry points:** VS Code `apps/vscode/src/extension.ts`; CLI bin `cline` → `apps/cli/src/index.ts` (apps/cli/package.json `"bin": {"cline": "src/index.ts"}`); hub daemon `@cline/core/hub/daemon-entry`; ACP mode `apps/cli/src/acp/index.ts`.
- **User-facing surfaces:** VS Code extension (`claude-dev` 4.1.3); npm CLI (`cline` 3.0.49) with interactive TUI, one-shot headless, JSON output, ACP mode; local hub WebSocket daemon + `cline-hub` dashboard webview; Tauri desktop example app (`apps/examples/desktop-app`, `@cline/code`); JetBrains via external plugin repo (CI workflow `ext-jb-test-integration.yml` triggers "IntelliJ Plugin Integration Test" in another repo) riding the legacy HostProvider/gRPC hostbridge (`apps/vscode/src/hosts/host-provider.ts:5-14`: "runs on two different platforms (VSCode extension and cline-core)"; `apps/vscode/proto/host/{diff,env,window,workspace}.proto`).
- **Extension mechanisms:** rules (AGENTS.md + legacy `.clinerules`), workflows, Skills (SKILL.md + YAML frontmatter), plugins, subprocess hooks, MCP (client + marketplace in extension), cron/event automation specs, remote-config managed instructions.
- **Tests:** 216 `*.test.ts` in sdk/, 177 in apps/vscode/src, 146 in apps/cli/src (Vitest/bun), plus extension integration (@vscode/test-electron), Playwright e2e, and `evals/` (smoke tests + cline-bench, run against the headless CLI — evals/README.md:5).
- **Release/versioning:** unified release script `sdk/scripts/release.ts:5-17` publishes SDK packages and CLI to npm; CI workflows `sdk-publish.yml`, `cli-publish.yml`, `desktop-publish.yml`, `ext-vscode-publish-{stable,nightly}.yml`, `ui-publish.yml`. External (npm registry, checked 2026-08-04): `@cline/core@0.0.69` (latest + nightly dist-tags), `@cline/sdk@0.0.69`, `cline@3.0.49` — versions exactly match the repo.
- **Maturity:** first commit 2024-07-05, HEAD 2026-08-04; 2,460 commits since 2026-01-01, 425 since 2026-07-01 (git log). Very high cadence.
- **Vendor coupling:** Cline account auth (WorkOS device auth per root script `verify:workos-device-auth`), `cline` first-party provider requiring `CLINE_API_KEY` (AGENTS.md CLI section), PostHog telemetry (core-events.ts:755 mentions "downstream PostHog joins"; `posthog-node` in extension deps), remote-config control plane (`sdk-remote-config-control-plane`). All bypassable with BYOK providers.

**Engine/host boundary verdict (the central question): REAL, not aspirational.** Evidence chain: (1) publishable packages with `files: ["dist"]`, exports maps and npm metadata (sdk/packages/agents/package.json); (2) release automation + `check-publish.ts`; (3) external npm registry confirms published versions matching the repo; (4) two in-repo consumers with different processes — the CLI (no VS Code API anywhere) and the extension via injected executors; (5) `RuntimeHost` abstraction with `LocalRuntimeHost` / `HubRuntimeHost` / `RemoteRuntimeHost` (`sdk/packages/core/src/runtime/host/runtime-host.ts:107-143`); (6) the hub is a WebSocket server daemon with per-process auth tokens brokering sessions to any client (`sdk/packages/core/src/hub/server/`); (7) an ACP agent implementation makes the engine drivable by third-party editors (`apps/cli/src/acp/acpAgent.ts:24-25` imports `@agentclientprotocol/sdk`). Additionally the *legacy* engine's host abstraction (protobuf hostbridge, `proto/host/*.proto` + `src/hosts/external/host-bridge-client-manager.ts`) survives inside `apps/vscode` for the JetBrains/standalone path — so there are two generations of host abstraction in one repo.

## B. One agent turn (VS Code host), keystroke → persisted state

1. **Input ingestion:** webview React app sends protobuf-encoded requests over `postMessage`; `handleGrpcRequest` in `apps/vscode/src/core/controller/grpc-handler.ts:23-66` dispatches unary/streaming handlers (a gRPC-shaped RPC layer over the webview channel, service defs in `apps/vscode/proto/cline/*.proto`). A new task lands in `controller/task/newTask.ts:16-45` (`NewTaskRequest` carrying text, images, `PlanActMode`, per-task `autoApprovalSettings` merged with globals, browserSettings, reasoning-effort settings).
2. **Session construction:** `SdkController`/`cline-session-factory.ts` + `sdk-session-config-builder.ts` build a `StartSessionInput`; `ClineCore.start(...)` normalizes config and delegates to `RuntimeHost` selection in `packages/core/src/runtime/host.ts` (`LocalRuntimeHost` in-process; hub variants otherwise) → `local-runtime-bootstrap.ts` feeds `DefaultRuntimeBuilder` (tools, hooks, extensions, instruction watcher, telemetry) → constructs an `Agent` from `@cline/agents` (flow per ARCHITECTURE.md:119-127, corroborated by file presence and imports).
3. **System prompt assembly:** `DEFAULT_CLINE_SYSTEM_PROMPT` (`sdk/packages/shared/src/prompt/system.ts:1-35`) — remarkably small (whole file incl. the YOLO variant is 6.6 KB; each prompt ≈700–900 tokens) with `{{CLINE_RULES}}`/`{{CLINE_METADATA}}` slots. Rules come from the config watcher system: workspace/global `AGENTS.md`, legacy `.clinerules` file-or-dir, `rules/`, `workflows/`, `skills/` dirs (`user-instruction-config-loader.ts:483-501, 569`; `shared/src/storage/paths.ts:34-44`). Plan/act adds `MODE_TAG_INSTRUCTIONS` + `PLAN_MODE_INSTRUCTIONS[_MANUAL_SWITCH]` (`shared/src/prompt/cline.ts:21-57`).
4. **Context selection:** file mentions parsed in `apps/vscode/src/core/mentions/index.ts`; user messages wrapped in `<user_input mode="...">` tags (cline.ts:23).
5. **Request construction & provider abstraction:** `AgentRuntime.run()` (`sdk/packages/agents/src/agent-runtime.ts:655-802`) → `generateAssistantMessageWithOverflowRecovery` → `AgentModel` built by the `@cline/llms` gateway registry (`createGateway`, agent-runtime.ts:1-5). ~150 generated provider IDs (`llms/src/providers/provider-ids.generated.ts`) resolve onto ~9 vendor implementation families (`providers/vendors/`: anthropic, bedrock, google, vertex, mistral, ollama, openai, openai-compatible, community) executed through Vercel AI SDK `streamText` (`providers/ai-sdk.ts:23-25, 1247`). Model-specific branches live in `vendors/*` and `providers/routing/` (e.g. `anthropic-compatible.ts:132,222` handles `cache_control` placement) and `providers/middleware/` (retry-empty-response, split-tool-images).
6. **Streaming:** `AgentModelEvent` deltas assembled per part; reasoning deltas handled at agent-runtime.ts:222; tool-call fragments assembled by index/toolCallId (agent-runtime.ts:1099-1130).
7. **Tool-call parsing:** none of the legacy XML — tools are native structured tool calls; assistant message parts filtered with `part.type === "tool-call"` (agent-runtime.ts:711-714). Inputs run through `normalizeJsonLikeStringsForSchema` against the tool's JSON Schema (agent-runtime.ts:1546); schemas are `zodToJsonSchema(...)` (definitions.ts:621,675).
8. **Authorization:** per-tool `ToolPolicy {enabled, autoApprove}` resolved with hook overrides (agent-runtime.ts:1576-1594). `autoApprove: false` triggers the host's `requestToolApproval` callback; **no callback configured ⇒ denied** (agent-runtime.ts:1604-1615). The extension forces `autoApprove:false` for all read/edit/command/web/MCP tools and evaluates its AutoApproveBar settings live inside the callback (`apps/vscode/src/sdk/sdk-tool-policies.ts:7-40`); note the comment "The SDK defaults unlisted tools to auto-approved."
9. **Execution locus:** extension-host process. `prepared.tool.execute(input, context)` (agent-runtime.ts:1668-1688) with per-tool `timeoutMs` (`withTimeout`), abort signal, and `emitUpdate` streaming. Hosts inject executors: VS Code suppresses the SDK's `run_commands` and swaps in a terminal-integrated tool with foreground (VscodeTerminalManager, shell integration) and background (SDK `createShellExecutor` = `child_process.spawn` with kill-tree timeout, `executors/bash.ts:127-227`) modes (`vscode-run-commands-tool.ts:1-12`, `vscode-session-host.ts:102-116,164`); `editor` is replaced with a diff-view pipeline (`vscode-session-host.ts:58-61`); reads via `vscode-file-read-executor.ts`.
10. **Observation return:** tool result messages appended to the transcript (agent-runtime.ts:764-773); outputs capped (48,000 chars for command/read/search output, 2,000 lines / 2,000 chars-per-line reads, `executors/output-limits.ts:18-50`).
11. **Loop termination:** iterate while `iteration < maxIterations`; a response with zero tool calls ends the run "completed" (after optional completion-reminder nudges), or a tool with `lifecycle.completesRun` — `submit_and_exit`, the `attempt_completion` analog — terminates via `findCompletingToolMessage` (agent-runtime.ts:739-797, 1492-1512; definitions.ts:801-831). Exceeding maxIterations throws (agent-runtime.ts:800-802).
12. **State persistence:** core owns it — SQLite session manifests (`session/stores/session-manifest-store.ts`; `shared/src/db/sqlite-db.ts:144` bun/better-sqlite3) + atomic-file messages artifacts (`stores/atomic-file.ts`, `conversation-store.ts`); compaction state in `${sessionId}.compaction.json` (`services/session-artifacts.ts:85`). Root-session persistence is lazy (no row until first accepted user turn, ARCHITECTURE.md:160-165, doc). The extension mirrors into legacy task history (`sdk-task-history.ts`).
13. **Checkpoints:** now real-repo git plumbing, not shadow git: snapshot commits built with a temporary index (`write-tree`/`commit-tree`, stash-shaped 2-3 parent commits) stored under private refs `refs/cline/checkpoints/{sessionId}/` (`core/src/hooks/checkpoint-hooks.ts:111-153, 250-263`). Restore is destructive-with-transaction: `stash push --include-untracked` snapshot ref `refs/cline/restore-transactions/<id>`, then `git reset --hard` + `git clean -fd`, rollback on failure (`session/checkpoint-restore.ts:43-143`).
14. **Context-window management:** compaction is a core-owned prepare-turn pipeline; default strategy "agentic" (LLM summarizer) with `preserveRecentTokens` floor and a deterministic basic fallback ("recovery must not depend on another" model call) (`extensions/context/compaction.ts:48,167-170,285-290`). Canonical transcript stays append-only at full fidelity; compaction is a projection. In-loop overflow: compact once and retry; otherwise terminal messages (agent-runtime.ts:58-73, `overflowRecoveryAttempted` 664).
15. **Failure/retry/cancel:** provider errors classified (`classifyProviderError`, agent-runtime.ts:2); empty-response retry middleware (`llms/providers/middleware/retry-empty-response.ts`); abort via `AbortController`/`ControlledStopError` → status "aborted" (agent-runtime.ts:803-825); per-tool timeouts and `retryable/maxRetries` flags (definitions.ts:622-624).

## D. Governing philosophy

Engine-as-product with hosts as adapters. The 2024–2025 Cline was a VS Code extension whose loop lived in the extension; at this commit the company has inverted the architecture: a layered, published SDK (`shared→llms→agents→core`) owns the loop, persistence, compaction, tools, MCP, automation; hosts (VS Code, CLI/TUI, hub dashboard, ACP, desktop example) inject executors and approval callbacks through explicit seams (RuntimeHost, defaultToolExecutors, hooks, config watchers — ARCHITECTURE.md "Design Seams", corroborated by vscode-session-host.ts). Complexities owned: provider normalization (~150 IDs over one AI-SDK execution path), context compaction with canonical-transcript preservation, durable automation (SQLite cron queue), session brokering (hub). Complexities pushed to users/ecosystem: safety (approval prompts, yolo is a first-class preset), provider quality variance (community vendor catalog is generated, largely untested per-provider), JetBrains support (external repo), and the migration debt of the old UI protocol (the extension keeps its entire legacy proto/gRPC webview surface and translates it message-by-message to SDK events).

## E. Hidden tradeoffs

- **CONFIRMED — doc drift in the flagship architecture doc:** ARCHITECTURE.md:497-515 tells contributors to start at `packages/agents/src/agent.ts`, `agent-step.ts`, `tool-use.ts`; none exist — `agents/src` contains only `agent-runtime.ts` + `index.ts` (ls). Implementation beats doc; the doc lost.
- **CONFIRMED — two MCP clients with divergent capability:** SDK core client is stdio-only and pins protocol "2024-11-05" (client.ts:44,195-200) while the extension's McpHub supports stdio/SSE/streamableHTTP via the official SDK (McpHub.ts:7-9). Headless/CLI MCP is therefore weaker than IDE MCP.
- **CONFIRMED — plan mode is prompt-enforced for shell:** plan preset keeps `enableBash: true` despite its own "read-only, no shell access" comment (presets.ts:43-55); code comment admits "the mitigation for plan-mode mutations is prompting plus mode-switch notices, not tool removal" (cline.ts:26-30). A model can mutate state in plan mode via run_commands if commands are auto-approved.
- **CONFIRMED — checkpoint restore is destructive on the user's real repo:** `git reset --hard` + `git clean -fd` with a stash-transaction safety net (checkpoint-restore.ts:43-143). Shadow-git isolation is gone; a rollback failure path exists but ends in "Workspace snapshot and rollback both failed" (line 113).
- **CONFIRMED — SDK default posture is auto-approve:** "The SDK defaults unlisted tools to auto-approved" (sdk-tool-policies.ts:7-9); safe behavior in the extension depends on the host enumerating every tool name (incl. `server__tool` MCP names) into policies. Embedders who skip this get a yolo-ish agent. Mitigant: missing approval callback ⇒ deny (agent-runtime.ts:1610-1614).
- **CONFIRMED — massive translation layer in the extension:** ~90 bridge files in `apps/vscode/src/sdk/` (message-translator, coordinators for followups/compaction/diff-edit/mode/etc.) re-encode SDK events into the legacy webview proto. State exists in three representations (SDK session, ClineMessage history, webview) — classic duplication surface, though heavily unit-tested.
- **CONFIRMED — tiny system prompt, schema'd tools:** both system prompts together are 6.6 KB (system.ts wc; ≈800 tokens each), versus legacy Cline's multi-thousand-token XML tool manual. Token overhead moved into JSON tool schemas, which are per-model-cached and far smaller.
- **CONFIRMED — no fuzzy edit matching:** editor requires a unique exact `old_text` match (editor.ts:181-195). Robust against silent mis-edits, but stale-context edits hard-fail and burn turns (mitigated by VS Code's replacement diff-pipeline executor).
- **RISK — pre-1.0 SDK churn:** all SDK packages are 0.0.69; `@cline/ui` is 0.2.0-next.2; internal `kanban-migration/` and `vscode-rollout` app signal live migrations. Embedders face API instability.
- **RISK — provider catalog breadth vs. depth:** ~150 generated provider IDs share ~9 vendor code paths; only anthropic/bedrock/ollama/openai/vertex/minimax/community have tests in vendors/ (ls). Long-tail providers are config-generated and effectively untested.
- **RISK — approval-gated ≠ sandboxed:** every boundary is a UI prompt or policy bit evaluated in-process; no OS-level enforcement (no seccomp/sandbox-exec/container found anywhere in sdk/ or apps/). With commands auto-approved, data egress via fetch_web_content/bash is unimpeded; no prompt-injection defense was found.

## G. Benchmark inputs

No VS Code required. Fairness blocker: none, though the hub daemon auto-spawn (AGENTS.md CLI section) should be accounted for in CI.
- **Fixed model endpoint injection:** provider env vars (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, ...), `cline auth`, or embed via SDK `AgentRuntimeConfigWithProvider {providerId, modelId, apiKey, baseUrl}` (agent-runtime.ts:113-127). openai-compatible vendor covers arbitrary endpoints.
- **Scripting approvals:** yolo preset sets `{enabled:true, autoApprove:true}` for `*` and every default tool (presets.ts:137-158); yolo also swaps to the unattended system prompt with mandatory `submit_and_exit` (system.ts YOLO block; ARCHITECTURE.md:129-136).

## H. Portability-adapter inputs

- **Native mechanisms an adapter would use:** AGENTS.md at workspace root + global (`user-instruction-config-loader.ts:483-501`); `rules/`, `workflows/`, `skills/` (SKILL.md + frontmatter, loader:24,206) under `.cline/` or legacy `.clinerules/` (paths.ts:34-44); subprocess hook files (hook-file-hooks.ts) for lifecycle policy; cron `*.md` specs with YAML frontmatter for scheduled/event runs (ARCHITECTURE.md:417-491, dirs verified under core/src/cron/); `mcpServers` JSON for optional tools; git checkpoints already ride real git refs.
- **What Cline would silently fight:** (1) agentic compaction summarizes away tool-result detail (`summarizeToolResults`, compaction.ts:118) — long methodologies must persist state to files, which Cline's own design encourages; (2) plan/act mode tags rewrite message envelopes (`<user_input mode>`), confusing transcripts consumed elsewhere; (3) approval gates block unattended verification unless yolo preset (which also swaps the system prompt and removes ask_question — presets.ts:96-108), so "unattended but careful" needs custom ToolPolicies via SDK rather than the CLI yolo flag; (4) hub-owned chat workspaces seed their own AGENTS.md (ARCHITECTURE.md:167-175, doc); (5) checkpoint refs pollute `refs/cline/*` in the real repo.
- **Spec→plan→tests→implement→review→verify→PR unattended:** highly feasible — headless CLI + yolo policies + hooks for gating + skills for procedure + cron for scheduling; the YOLO prompt already encodes a fix→test→iterate→submit_and_exit loop (system.ts). Missing pieces: no built-in PR tool (shell out to `gh`), no OS sandbox for safe unattended runs.

## Strengths / weaknesses / fit

**Strengths:** genuinely consumable engine (published, versioned, two real in-repo consumers + ACP); clean stateless-loop/stateful-core split; schema'd tools with host-injected executors; canonical-transcript-preserving compaction; durable SQLite-backed automation; headless CLI with JSON output; enormous provider surface; strong test density incl. loop tests (agent-runtime.test.ts, agent-runtime.provider-form.test.ts).
**Weaknesses:** pre-1.0 API churn; dual legacy/new host bridges and dual MCP clients to maintain; safety is entirely prompt/policy-level; plan mode's shell is honor-system; provider long tail untested; extension bridge complexity; stale architecture docs.
**Best fit:** teams wanting one engine across IDE + CLI + CI; embedding an agent loop in a product (Node/Bun); unattended automation with file-based specs. **Poor fit:** environments requiring OS-enforced isolation; JetBrains-first shops (external, older engine path); anyone needing a stable 1.x SDK contract today.

The claim was aspirational in earlier eras (the legacy gRPC "standalone" bridge still in-tree is that era's artifact); here it is the shipped architecture.
